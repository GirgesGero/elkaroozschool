# Plan: إعادة تصنيف موسوعة الكتاب المقدس إلى عشرة أقسام

## Goal
إعادة تصنيف **جميع الأقسام الـ36 الحالية** من الأجنحة الأربعة تحت الأقسام العشرة المطلوبة، لتكون الأقسام العشرة هي التصنيف الأساسي الظاهر في الواجهة.

## Current context / assumptions

- مساحة العمل: `E:/drive progect/ELKAROOZ SCHOOL`، والواجهة داخل `frontend/`.
- نقطة العرض الحالية: `frontend/src/components/Bible/WingSelector.tsx`، وتُستخدم من `frontend/src/app/bible/page.tsx`.
- `frontend/public/storage/bible-dataset/v1/categories.json` يحوي أربع فئات قديمة، و`sections.json` يحوي 36 قسمًا فرعيًا. harness `frontend/scripts/verify-encyclopedia.mjs` يتحقق من أعداد مصدر البيانات (4 فئات/36 قسمًا).
- التغيير المطلوب إعادة تصنيف في الواجهة فقط: أبقِ ملفات JSON و`category_id` القديمة كما هي حتى لا تتأثر آلية التحميل والفهرسة وصفحات المحتوى؛ استخدم أكواد الأقسام الموجودة لبناء التصنيف الجديد.
- كل كود من الأقسام الـ36 يجب أن يظهر مرة واحدة بالضبط في القائمة الجديدة. التوزيع الكامل موضح في القسم التالي. أبقِ العناوين الأصلية للأقسام الفرعية ولا تخترع محتوى أو روابط.
- قسم المخطوطات لا يملك قسمًا مطابقًا ضمن البيانات الحالية؛ اعرضه فارغًا برسالة واضحة. قسم الماراثون يضم `sec-06` ورابطًا إضافيًا إلى `/marathon`.
- لا تغيير على قاعدة البيانات أو Supabase أو API أو backend أو النشر. التغيير في frontend واختباراته فقط؛ لا push. نفّذ commits محلية صغيرة بعد نجاح الاختبارات ومراجعة diff.

## Architecture / proposed approach
أنشئ تعريفًا ثابتًا واحدًا للأقسام العشرة في `frontend/src/lib/bible/encyclopedia-sections.ts`، وكل قسم يحتوي أكواد الأقسام القديمة التابعة له. يبني `WingSelector` المجموعات من هذا التعريف ومن بيانات `categories[].sections` المحملة حاليًا، ويعرض كل الأقسام الـ36 مرة واحدة في التصنيف الجديد؛ أزل عرض الأجنحة الأربعة كجذور واجهة، ولا تغيّر taxonomy المصدرية أو خدمات API. تحقّق آليًا من تغطية جميع الأكواد دون تكرار أو نقص.

## Step-by-step tasks

### 1. اكتب اختبار تغطية التصنيف قبل التنفيذ (2–5 دقائق)
- أنشئ `frontend/tests/encyclopedia-sections.test.ts` قبل ملف المصدر.
- اختبر ترتيب الأسماء العشرة حرفيًا، تفرد المعرّفات، وتعيين كل كود مرة واحدة فقط. قارن كل الأكواد الموزعة بالأكواد الفعلية في `frontend/public/storage/bible-dataset/v1/sections.json` لإثبات عدم وجود نقص أو زيادة؛ تحقق أيضًا أن `sec-06` ضمن الماراثون وأن وجهته الإضافية `/marathon`.
- استخدم `readFileSync(new URL('../public/storage/bible-dataset/v1/sections.json', import.meta.url), 'utf8')` في الاختبار إذا لم يدعم إعداد TypeScript استيراد JSON مباشرة.
- شغّل RED:
  ```bash
  cd frontend && npm test -- tests/encyclopedia-sections.test.ts
  ```
  المتوقع: فشل بسبب غياب وحدة `@/lib/bible/encyclopedia-sections`، لا بسبب إعداد Vitest أو تحميل dataset.

### 2. أنشئ التعريف الكامل للأقسام العشرة (2–5 دقائق)
- أنشئ `frontend/src/lib/bible/encyclopedia-sections.ts` بالتوزيع الوارد في جدول «التوزيع الصريح المقترح» أعلاه. لا تغيّر أكواد الأقسام أو عناوين الأقسام الفرعية الأصلية.
- استخدم النوع التالي، وصدّر القائمة باسم `ENCYCLOPEDIA_SECTIONS`:
  ```ts
  export type EncyclopediaSection = {
    id: string;
    title: string;
    icon: string;
    sectionCodes: string[];
    route?: '/marathon';
  };
  ```
- يجب أن تحتوي القائمة 10 عناصر مرتبة كما طلب المستخدم؛ `manuscripts.sectionCodes` قائمة فارغة، و`marathon` يحمل `sectionCodes: ['sec-06']` و`route: '/marathon'`.
- أعد الاختبار:
  ```bash
  cd frontend && npm test -- tests/encyclopedia-sections.test.ts
  ```
  المتوقع: نجاح الترتيب والتغطية (36 كودًا فريدًا ومطابقًا للـJSON). راجع diff ثم commit محليًا: `git add frontend/src/lib/bible/encyclopedia-sections.ts frontend/tests/encyclopedia-sections.test.ts && git commit -m "Define ten Bible encyclopedia categories"`.

### 3. اكتب اختبار واجهة يثبت إعادة التصنيف الكامل (2–5 دقائق)
- أنشئ `frontend/tests/WingSelector.test.tsx` باستخدام Vitest وTesting Library، ومرّر fixture من `BibleCategory[]` يحتوي بيانات الأقسام الـ36.
- اختبر أن العرض الافتراضي يُظهر العناوين العشرة بالترتيب، ولا يعرض الأجنحة الأربعة كجذور، ويعرض كل قسم فرعي قديم مرة واحدة داخل القسم الجديد المحدد له. تحقق من الروابط `/bible/section/<code>` ومن `/marathon`، ومن رسالة المجموعة الفارغة للمخطوطات.
- شغّل RED قبل تعديل المكوّن:
  ```bash
  cd frontend && npm test -- tests/WingSelector.test.tsx
  ```
  المتوقع: فشل assertions الخاصة بالتقسيم والعناوين لأن `WingSelector` الحالية تعرض الفئات الأربع.

### 4. طبّق التجميع الجديد في الواجهة (2–5 دقائق)
- عدّل `frontend/src/components/Bible/WingSelector.tsx`: أنشئ lookup للأقسام من `categories.flatMap(category => category.sections ?? [])` حسب `code`، ثم كوّن الأقسام العشرة باستخدام `ENCYCLOPEDIA_SECTIONS[].sectionCodes`.
- اجعل الأقسام العشرة هي جذور الواجهة الوحيدة؛ لا تُبقِ تبويبًا أو قائمةً تعرض الأجنحة الأربعة كتصنيف بديل. اعرض داخل كل قسم عناوينه الفرعية الأصلية وروابطها `/bible/section/<code>`، واحسب عدد الوثائق من عناصره. اعرض «لا توجد مواد مضافة بعد» لقسم المخطوطات؛ لا رابط وهميًا. أضف رابط `/marathon` إلى قسم الماراثون بالإضافة إلى `sec-06`.
- احتفظ بالبحث والتوسيع/الطي لكن اجعلهما يعملان على مجموعات الأقسام العشرة. حافظ على RTL والتصميم responsive واستخدم tokens/classes الموجودة (`bg-nav`, `border-line`, `text-content`, `text-gold`) بدل ألوان ثابتة جديدة.
- وسّع اختبار المكوّن ليتحقق من أن كل الأقسام الـ36 تظهر مرة واحدة في المجموعة المطلوبة وأن الأجنحة الأربعة لا تظهر كجذور. شغّل الاختبار لإثبات GREEN:
  ```bash
  cd frontend && npm test -- tests/WingSelector.test.tsx
  ```
  المتوقع: نجاح assertions العشرة/36 والروابط، مع اختفاء تصنيف الأجنحة الأربعة من الواجهة. بعد `git diff --check` راجع diff ثم commit محليًا: `git add frontend/src/components/Bible/WingSelector.tsx frontend/tests/WingSelector.test.tsx && git commit -m "Reclassify all Bible encyclopedia sections"`.

### 5. تحقق من سلامة taxonomy القديمة والأنواع والبناء (2–5 دقائق)
- لا تعدّل `categories.json` أو `sections.json` أو `manifest.json` ما دام التغيير واجهة عرض فقط.
- من `frontend/` شغّل:
  ```bash
  npm test -- tests/encyclopedia-sections.test.ts tests/WingSelector.test.tsx
  npm run typecheck
  node --experimental-strip-types scripts/verify-encyclopedia.mjs
  npm run build
  ```
- المتوقع: اختبارات Vitest ناجحة؛ `tsc --noEmit` يخرج برمز 0؛ harness الموسوعة يطبع نجاح taxonomy الحالية (`4 categories`, `36 sections`) وبقية checks؛ وNext.js build يكتمل برمز 0. لا تعلن نجاح build إذا تعطل بسبب متغيرات بيئة أو اعتماديات؛ سجّل السبب الدقيق.
- شغّل `git diff --check` وتأكد أن ملفات التعديل محصورة في المصدر/الاختبار المقصودين، ولا توجد migrations أو تغييرات dataset أو ملفات اعتماد.

### 6. تحقق بصري محلي قبل التسليم (2–5 دقائق)
- شغّل `cd frontend && npm run dev` وافتح `/bible` محليًا.
- تحقق يدويًا من RTL وترتيب الأقسام العشرة، عدم بقاء الأجنحة الأربعة كجذور أو تبويب، ظهور كل قسم من الـ36 مرة واحدة تحت مجموعته، روابط الأقسام ومسار الماراثون، رسالة الفراغ للمخطوطات، وعمل البحث والتوسيع/الطي على المجموعات الجديدة. تحقق على عرض الهاتف والسطح المكتبي، ثم أوقف خادم التطوير وسجّل النتيجة. لا تنشر ولا تدفع التغييرات إلى remote.

## Tests / validation

- TDD لكل تغيير سلوكي: اكتب assertion أولًا، شغّل الاختبار وأثبت فشله للسبب المتوقع، نفّذ أقل تغيير، ثم أعد الاختبار حتى ينجح؛ لا تتجاوز RED/GREEN.
- اختبارات العقد والتغطية: `frontend/tests/encyclopedia-sections.test.ts` تقرأ أكواد JSON الفعلية وتثبت التغطية الدقيقة للـ36 كودًا مرة واحدة بلا نقص أو تكرار أو أكواد مجهولة.
- اختبارات الواجهة: `frontend/tests/WingSelector.test.tsx` تثبت أن التصنيف الرئيسي 10 أقسام بدل الأجنحة الأربعة، وأن الـ36 قسمًا فرعيًا تظهر مرة واحدة في المجموعات المحددة، مع صحة الروابط وحالة المخطوطات الفارغة.
- التحقق النهائي: Vitest المستهدف، `npm run typecheck`، `node --experimental-strip-types scripts/verify-encyclopedia.mjs`، `npm run build`، `git diff --check`، وفحص `/bible` محليًا.
- بعد كل مجموعة ناجحة، راجع diff ثم أنشئ commit محليًا مستقلًا. لا push ولا deploy.

## Risks, tradeoffs, and open questions

- **تعيينات تقريبية تحتاج اعتمادًا:** `sec-agpeya` و`sec-10` (صلوات الكنيسة) أُدرجا مؤقتًا في «الكتاب المقدس» لعدم وجود تصنيف للصلوات ضمن القائمة المطلوبة؛ `sec-34` (لغة قبطية) أُدرج في «ترجمات الكتاب المقدس»؛ و`sec-08` (شخصيات الكنيسة) أُدرج في «موسوعة الشخصيات الكتابية». هذه ليست مطابقات دقيقة، فاعتمدها المستخدم قبل التنفيذ أو حدّد بديلًا. لا تغيّر العناوين الأصلية ولا تصف هذه المواد وصفًا غير صحيح.
- **المخطوطات:** لا يوجد قسم مخطوطات بين الأقسام الـ36 الحالية؛ سيكون هذا القسم الرئيسي فارغًا حتى إضافة محتوى فعلي لاحقًا.
- **تفسير الكتاب المقدس واسع:** يضم أقسامًا لاهوتية وتعليمية كثيرة كانت مصنفة تاريخيًا في أجنحة مختلفة؛ تبقى عناوينها الأصلية كما هي تحت التصنيف الجديد.
- **التوافق مع البيانات:** تبقى `category_id` والقيم الأربع في ملفات المصدر كما هي للاستخدام الداخلي. قد تستمر breadcrumbs أو نتائج API في عرض تصنيف المصدر القديم؛ هذه الخطة لا تغيّر API أو صفحات المقالات.
- **الماراثون:** `sec-06` يبقى قابلًا للتصفح عبر رابط القسم، والرابط الإضافي يفتح `/marathon` الحالية؛ لا تغيير على صلاحيات أو وظائف الماراثون.
